# 0) 목적
운영자가 **빠르고 일관되게** 핵심 업무(이벤트 승인, 당첨자 선정, 알림)를 수행하고,
장애 시 **안전하게 복구/되돌리기** 하기 위한 표준 절차(SOP)를 문서화한다.

# 1) 연락/의사소통
- **주 담당**: Admin
- **장애 알림**: 이메일/슬랙
- **외부 공지**: 사이트 배너, 이메일 템플릿

# 2) 표준 체크리스트 (공통)
- [ ] 관리자 권한 확인
- [ ] 영향 범위 파악 (대상 이벤트/사용자)
- [ ] 되돌리기 경로 확보 (DB 백업)
- [ ] 액션 실행 전 2차 확인

# 3) 이벤트 승인 Runbook

## 3.1 사전점검
- [ ] 이벤트 상태 = **pending_approval**
- [ ] 공연 정보 확인 (제목, 날짜, 장소)
- [ ] 파트너 정보 확인 (이름, 연락처)
- [ ] 티켓 수 및 응모 기간 확인
- [ ] 부적절한 내용/허위 정보 여부 점검

## 3.2 승인 실행
1. 관리자 대시보드 `/admin/events` 접근
2. 이벤트 상세 확인
3. **승인** 버튼 클릭
4. 확인 모달 → 승인 확정
5. 결과: `status = approved`, `approved_at = now()`

## 3.3 거부 실행
1. 거부 사유 명확히 작성 (필수)
2. **거부** 버튼 클릭
3. 확인 모달 + 사유 입력 → 거부 확정
4. 결과: `status = rejected`, 사유 기록
5. 파트너에게 알림 발송 (향후)

## 3.4 되돌리기
- **조건**: 승인/거부 오류
- **절차**:
  1. DB에서 수동으로 `status` 변경
  2. 감사 로그 기록
  3. 파트너에게 정정 안내 (향후)

# 4) 당첨자 선정 Runbook

## 4.1 사전점검
- [ ] 이벤트 상태 = **approved**
- [ ] 응모 기간 종료 확인 (`ends_at < now()`)
- [ ] 응모자 수 확인
- [ ] 티켓 수 확인

## 4.2 수동 선정
1. `/admin/entries` 접근
2. 이벤트 선택 → 응모자 목록 조회
3. 체크박스로 당첨자 선택
4. **당첨자로 선정** 버튼 클릭
5. 확인 모달 → N명 선정 확정
6. 결과: `selection_status = selected`, `selected_at = now()`
7. 당첨자에게 알림 발송 (향후)

## 4.3 랜덤 선정 (향후)
1. 티켓 수 입력
2. **랜덤 선정** 버튼 클릭
3. 확인 모달 → 알고리즘 실행
4. 결과 확인 및 확정

## 4.4 일괄 미선정
1. **나머지 미선정 처리** 버튼 클릭
2. 확인 모달 → pending 응모를 rejected로 변경

## 4.5 되돌리기
- **조건**: 선정 오류
- **절차**:
  1. DB에서 `selection_status = pending`으로 복구
  2. 재선정 실행
  3. 당첨자에게 정정 안내

# 5) 관람 체크 Runbook

## 5.1 사전점검
- [ ] 공연 당일 또는 이후
- [ ] 당첨자(`selection_status = selected`) 목록 확인

## 5.2 관람 완료 처리
1. `/admin/entries` 접근
2. 이벤트 선택 → 당첨자 목록
3. 체크박스로 관람 완료자 선택
4. **관람 완료** 버튼 클릭
5. 결과: `attendance_status = checked_in`, `checked_in_at = now()`

## 5.3 미관람 처리
1. 체크박스로 미관람자 선택
2. **미관람** 버튼 클릭
3. 결과: `attendance_status = no_show`

# 6) 데이터 수정/정정 Runbook

## 6.1 중복 응모 정정
- **키**: `UNIQUE(campaign_id, contact_hash)`
- **절차**:
  1. 중복 레코드 확인
  2. 유효한 응모 1건만 남기고 나머지 삭제
  3. 감사 로그 기록

## 6.2 상태 정정
- 이벤트/응모 상태를 DB에서 직접 수정
- 변경 전후 스냅샷 기록
- 영향받은 사용자에게 안내

# 7) 장애 대응

## 7.1 장애 분류
| SEV | 정의               | 예시                      | 초기 대응      |
|-----|--------------------|---------------------------|----------------|
| 1   | 전면 중단          | 사이트 다운, DB 장애      | 배너 + 긴급 복구|
| 2   | 주요 기능 저하     | 응모 실패, 승인 지연      | 원인 파악 + 임시 조치|
| 3   | 일부 오류/지연     | 특정 이벤트 오류          | 모니터링       |

## 7.2 응모 실패 장애
- **증상**: 응모 오류율 급증
- **원인 확인**:
  1. DB 연결 상태
  2. Rate Limit 초과
  3. 중복 응모 차단
- **조치**:
  1. 배너 공지
  2. Rate Limit 임시 완화 (필요 시)
  3. 응모 기간 연장 검토

## 7.3 승인 지연
- **증상**: 3일 이상 승인 대기
- **조치**:
  1. 승인 대기 목록 점검
  2. 파트너에게 진행 상황 안내
  3. 우선순위 검토

# 8) 배포 체크리스트

## 8.1 배포 전
- [ ] 스테이징 환경 테스트 완료
- [ ] DB 마이그레이션 검증
- [ ] 롤백 계획 수립
- [ ] 배포 시간 공지 (필요 시)

## 8.2 배포 후
- [ ] 헬스체크 확인
- [ ] 핵심 플로우 테스트 (응모, 승인, 선정)
- [ ] 에러 로그 모니터링 (30분)
- [ ] 롤백 준비 상태 유지 (1시간)

# 10) 공지 템플릿

## 10.1 장애 공지
**제목**: [안내] 시스템 점검/장애 안내 (KST 시각)
**본문**:
```
현재 [기능]에 일시적인 오류가 발생하여 서비스 이용에 불편을 드리고 있습니다.
빠른 시일 내에 복구하겠습니다.
불편을 드려 죄송합니다.
```

## 10.2 정정 공지
**제목**: [중요] 당첨자 정정 안내
**본문**:
```
[이벤트명]의 당첨자 선정 과정에서 오류가 발생하여 정정합니다.
정정 사유: [사유]
기존 당첨자: [N명]
정정 당첨자: [N명]
불편을 드려 죄송합니다.
```
